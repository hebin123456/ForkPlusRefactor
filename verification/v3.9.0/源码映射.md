# ForkPlus v3.9.0 → Avalonia 跨平台重构：源码映射与对照手册

> 本手册基于 **ForkPlus v3.9.0 真实源码**（`src/` 共 1862 个文件，主工程 `ForkPlus/`）审计生成，
> 作为 `verification/v3.9.0/` 下 56 张功能截图 + `操作步骤.md` 的**逻辑层补充**。
> 截图告诉你"界面长什么样、点了什么"；本手册告诉你"这段代码在哪、平台依赖是什么、Avalonia 端怎么替换"。
> 三者配合，即可在重构时做逐个界面的像素级 / 行为级回归，不依赖 Windows 真机。

## 0. 结论速览

| 维度 | 结论 |
|---|---|
| **可行性** | ✅ 可行，工作量可控。csproj 注释本身也写明"暂未做跨平台 UI 迁移（A 方向）"，即架构上已在为迁移预留空间 |

## 1. 架构接缝：已有的平台抽象（最关键利好）

`Services/ServiceLocator.cs` 是一个轻量级服务定位器，注释明确写道：
> *"用于解耦业务层对 WPF 的直接依赖。迁移完成后可替换为正式 DI 容器。"*

它注册了 **7 个平台无关接口**，每个都有 `Wpf*` 实现。Avalonia 端只需为每个接口新增一个实现并在 `App.OnStartup` 注册即可。

| 接口 | WPF 实现 | 平台依赖 | Avalonia 替代实现 |
|---|---|---|---|
| `IDispatcher` | `WpfDispatcher` | WPF `Dispatcher` | `Avalonia.Threading.Dispatcher`（或 `Dispatcher.UIThread.Post`） |
| `IDesignModeService` | `WpfDesignModeService` | `DesignerProperties` | `Design.IsDesignMode`（`Avalonia.Styling`） |
| `IAppContext` | `WpfAppContext` | WPF 特定 | 跨平台通用实现（取 AppData 路径等） |
| `IClipboardService` | `WpfClipboardService` | WPF `Clipboard` | `Avalonia.Application.Current.Clipboard` |
| `ITimerService` | `WpfTimerService` | `DispatcherTimer` | `Avalonia.Threading.DispatcherTimer` |
| `IToastNotificationService` | `WpfToastNotificationService` | WinRT `ToastNotification`（CommunityToolkit.WinUI.Notifications） | Windows 用 WinUI Toast；macOS 用 `NSUserNotification`；Linux 用 libnotify (DBus) |
| `IWindowManagerService` | `WpfWindowManagerService` | `Application.Current.Windows` | `Avalonia.Application.Current.Windows` |

> **重构动作**：新增 `Services/Avalonia/` 目录，实现这 7 个接口；在 Avalonia 工程的 `App.OnStartup` 里把 `new WpfXxx(...)` 换成 `new AvaloniaXxx(...)`。业务层（ViewModels/Commands）因只依赖接口，**几乎零改动**。

## 2. 平台依赖清单（按替换成本排序）

### 2.1 核心 Git 引擎 `biturbo` —— ✅ 已跨平台（无需重写）

- 封装于 `Biturbo/Bt.cs`（56 个 `DllImport` 指向 `biturbo` 原生库）。
- `ForkPlus.csproj` 的 `RestoreBiturbo` target 显示三平台 asset：
  - Windows → `biturbo.dll` / Linux → `libbiturbo.so` / macOS → `libbiturbo.dylib`
- AI 的 Markdown→HTML 也走 biturbo（`Bt.bt_md_to_html`），同样跨平台。
- **结论**：Git 逻辑（提交图、Diff、Blame、Cherry-pick、Stash 等）全部复用，仅需在 Avalonia 工程里按平台引用对应原生库。

### 2.2 7 个平台服务接口 —— 见 §1（补 `Avalonia*` 实现）

### 2.3 WebView2 / AI 渲染 —— ⚠️ 替换成本最高

| 项 | 当前实现 | 文件 |
|---|---|---|
| AI 流式渲染控件 | `WebView2`（`Microsoft.Web.WebView2`） | `UI/Controls/AiStreamingWebView.xaml.cs` |
| AI 开发窗口 | `AiStreamingWebView` + WebView2 | `UI/Dialogs/AiDevelopmentWindow.xaml.cs` |
| AI 代码审查窗口 | `AiStreamingWebView` + `ExecuteScriptAsync` | `UI/Dialogs/AiCodeReviewWindow.xaml.cs` |
| AI 文本结果窗口 | `AiStreamingWebView` | `UI/Dialogs/AiTextResultWindow.xaml.cs` |
| AI 提交撰写窗口 | `AiStreamingWebView` | `UI/Dialogs/AiCommitComposerWindow.xaml.cs` |
| AI 建议预览窗口 | WebView2 | `UI/Dialogs/AiSuggestionPreviewWindow.xaml.cs` |
| Git-MM 引用窗口 | `WebView2EnvironmentHelper` | `UI/Dialogs/GitMmReferenceWindow.xaml.cs` |
| WebView2 环境创建 | `WebView2EnvironmentHelper.GetEnvironmentAsync()` | `UI/Dialogs/WebView2EnvironmentHelper.cs` |

**关键洞察（降低成本的方案）**：`AiStreamingWebView` 的 Markdown→HTML 实际由 **biturbo** 完成，WebView2 只负责最终 HTML 渲染与 `NavigateToString`。因此 Avalonia 端**可彻底抛弃 WebView2**，改用 `Markdown.Avalonia`（NuGet）直接把 Markdown 渲染为 Avalonia 控件树：

- 流式追加 → 维护 `StringBuilder`，节流后更新 `MarkdownScrollViewer.Markdown` 属性
- 主题跟随 → `MarkdownScrollViewer` 读取 `Application.ActualThemeVariant`，无需 `CoreWebView2PreferredColorScheme`
- JS→C# 消息（如 suggestion 按钮）→ 改为 Avalonia 原生按钮 + 命令绑定
- 滚动跟随 → 直接操作 `ScrollViewer` 的 `Offset`

> 仅当确实需要完整 Web 渲染（如内嵌交互式 HTML）时才引入 Avalonia WebView（`WebView.Avalonia` / CefNet），否则首选 `Markdown.Avalonia`。

### 2.4 编辑器与图表（WPF 专属控件）

| 当前包 | 用途 | 文件线索 | Avalonia 替代 |
|---|---|---|---|
| `AvalonEdit` 6.3.1 | 代码编辑器、Diff 编辑器 | `UI/Controls/Editor/`（96 文件）、`UI/Controls/Editor/Diff`（23）、`Merge`（5）、`Hex`（5） | `AvaloniaEdit`（AvalonEdit 的 Avalonia 移植，API 高度一致） |
| `OxyPlot.Wpf` 2.2.0 | 图表（提交热图/统计） | `UI/Controls/`（图表相关） | `OxyPlot.Avalonia` |

> 二者均有 Avalonia 官方/社区对应包，迁移以"换命名空间 + 调 API 差异"为主，逻辑可复用。

### 2.5 主题检测（两处实现，都要换）

| 位置 | 当前方式 | 风险 | Avalonia 替代 |
|---|---|---|---|
| `UI/SystemThemeHelper.cs` | WinRT `UISettings.ColorValuesChanged` | **Wine 下直接崩溃**（我已在验证中 IL patch 掉这两个方法） | `PlatformThemeVariantManager.ThemeVariantChanged` 事件 / `Application.ActualThemeVariant` |
| `App.xaml.cs` `GetSystemTheme()` | **Windows 注册表** `HKCU\...\Themes\Personalize\AppsUseLightTheme` | 非 Windows 无此键 | `PlatformThemeVariantManager` 或读取各平台原生 API |
| `App.xaml.cs` `SubscribeToUserPreferences()` | `Microsoft.Win32.SystemEvents.UserPreferenceChanged` | 非 Windows 不可用 | `PlatformThemeVariantManager.ThemeVariantChanged` |

> WPF 用 `ResourceDictionary` + `DynamicResource` 做主题热刷新（`App.ApplyCustomColors` / `ReloadThemeDictionary` 有详尽注释说明其机制）；Avalonia 用 `MergedDictionaries` + `ThemeVariant`，需注意 `DynamicResource` 行为差异与自定义颜色实时的实现方式。

### 2.6 凭据管理（DllImport，平台专属）

- `WindowsCredentialManager.cs`：用 `DllImport` 调用 Windows CredWrite/CredRead（DPAPI）。
- **Avalonia 替代**：抽象为 `ICredentialManager`，分平台实现——Windows 沿用现有 DllImport；macOS 用 Keychain；Linux 用 libsecret / Secret Service (DBus)。

### 2.7 Shell 集成（Windows 专属）

| 当前 | 文件 | Avalonia 替代 |
|---|---|---|
| `Microsoft-WindowsAPICodePack-Shell` | `Services/Wpf/WpfAppContext.cs` 等 | 文件关联/跳转列表用各平台原生 API；Avalonia 无内置等价，需 `Avalonia.Native` 或平台特定代码 |
| `AppUserModelID`（`shell32.dll` DllImport） | `App.xaml.cs` `NativeMethods` | 任务栏/跳转列表为 Windows 专属，跨平台可降级或各平台实现 |

### 2.8 Git 路径硬编码（跨平台必改）

`App.xaml.cs` 中 Git 相关路径**全部带 `.exe`**，且依赖 `sh.exe`/`bash.exe`（来自 Windows 版 Git）：

```csharp
public static string GitPath => ... ;                       // 期望 git.exe
public static string ShellPath => Path.Combine(..., "sh.exe");
public static string BashPath  => Path.Combine(..., "bash.exe");
// git-mm.exe、ConfigureGitInstanceWindow、AskPass（ForkPlus.AskPass.exe）
```

> **重构动作**：新增 `IGitPathResolver`，按 `RuntimeInformation.IsOSPlatform` 返回 `git`/`git-mm`（无扩展名）、`sh`/`bash`（来自 git 包或系统 PATH），并处理 Windows/macOS/Linux 差异。否则 Linux 下会找不到 `git.exe` 直接报错（见我截到的 `55-git-error-dialog.png`）。

### 2.9 WPF 特有 hack（需移除/替代）

| 位置 | 内容 | 说明 |
|---|---|---|
| `App.InitializeTextEditorContextMenuStyle()` | 反射访问 WPF 内部 `TextEditorContextMenu` 私有嵌套类型 | Avalonia 无此类型，直接用 AvaloniaEdit 原生 ContextMenu |
| `App.InitializeRenderMode()` | `RenderOptions.ProcessRenderMode = SoftwareOnly`（禁硬件加速） | Avalonia 通过 `AvaloniaLocator`/渲染器选项配置，无此 API |
| `RegisterScrollViewerContentTemplateGuard()` | 覆写 `ScrollViewer`/`ScrollContentPresenter` 的 `ContentTemplate` 元数据 | Avalonia 控件体系不同，需重新评估是否仍需此 guard |

## 4. 重构路线图（分阶段，建议顺序）

1. **阶段 1 · 工程骨架**
   - 新建 Avalonia 工程（`<UseWPF>false</UseWPF>`、`net10.0` 或 `net10.0-desktop`），引用 biturbo 三平台库。
   - 搬运 `Services/` 接口 + 新增 `Services/Avalonia/` 的 7 个实现，`App.OnStartup` 注册（替换 WPF 实现）。
   - 搬运 `Biturbo/`、`Git/`、`Accounts/`、`Settings/`（纯逻辑，几乎无 UI 依赖）。

2. **阶段 2 · 核心视图**
   - 主窗口、提交图、Diff（`AvaloniaEdit`）、文件树、本地改动/暂存区。
   - 验证 Git 数据在 Avalonia 下正常呈现（用本仓库截图做回归）。

3. **阶段 3 · 对话框（按优先级）**
   - 先迁偏好设置（7 标签页，平台风险低）。
   - 再迁高频：Clone / Checkout / Cherry-pick / Blame / Apply Stash / 冲突解决。
   - 140 个对话框可按"使用频率 + 平台依赖度"排序分批。

4. **阶段 4 · AI 渲染**
   - 用 `Markdown.Avalonia` 重写 `AiStreamingWebView`（见 §2.3），替换 5 个 AI 窗口的渲染层。
   - 保留 biturbo 的 Markdown→HTML（或改为 Markdown.Avalonia 直接解析）。

5. **阶段 5 · 平台服务收尾**
   - Toast（`IToastNotificationService` 分平台）、凭据（`ICredentialManager`）、Shell 集成、主题检测（§2.5）。
   - 修复 Git 路径解析（§2.8）、移除 WPF 反射/渲染模式 hack（§2.9）。

6. **阶段 6 · 验证回归**
   - 用 Wine 启动**原版** ForkPlus 截图，与 Avalonia 版逐项对比（本 `verification/v3.9.0/` 即为基线）。

## 5. 风险与注意点

1. **WebView2 在 Linux 无原生运行时**：务必用 `Markdown.Avalonia` 规避，不要试图在 Linux 跑 WebView2。
2. **Wine 下 `UISettings` 崩溃**：已在验证中通过 IL patch 临时绕过；Avalonia 端用 `PlatformThemeVariantManager` 从根上消除。
3. **主题热刷新机制差异**：WPF 靠 `ReloadThemeDictionary`（Add 新 + Remove 旧强制 DynamicResource 失效）；Avalonia 用 `MergedDictionaries` + `ThemeVariant`，需重新验证自定义颜色实时生效。
4. **Git 路径平台差异**：`git.exe`/`bash.exe` 必须改为无扩展名 + 平台解析，否则 Linux 直接报错（已截图为证：`55-git-error-dialog.png`）。
5. **反射 hack 不可用**：`TextEditorContextMenu` 反射、`ScrollViewer` 元数据覆写等在 Avalonia 需换实现或移除。
6. **245 个 XAML 转换工作量**：WPF XAML 与 Avalonia XAML 语法接近但命名空间/部分控件不同，建议用脚本批量改命名空间 + 人工核对差异控件。

- **截图**：`verification/v3.9.0/*.png`（56 张），按界面分组命名；`操作步骤.md` 标注每步点击坐标/菜单路径。

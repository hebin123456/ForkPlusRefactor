# ForkPlus 跨平台（Avalonia）重构工作量评估

> 数据来源：对 `ForkPlus` v3.9.0 仓库 `src/` 的真实源码审计（非估算推断）。
> 截至 2026-08-09，主工程 + 6 个子项目，全部 `net10.0-windows10.0.19041.0`。

## 0. 一句话结论

**核心业务逻辑（Git 引擎 + 命令层）基本不用重写；成本几乎全在 UI 层。**
总工作量约 **235–410 人天（≈1 名工程师 1–1.8 年）**；考虑编辑器兼容性与真机回归风险，建议按 **280–530 人天（1.3–2.4 人年）** 立项。一个 4–5 人团队可在 **3–5 个月** 内完成。

## 3. 关键利好（能省下的工作量）

1. **Git 引擎 biturbo 跨平台** —— 核心 Git 操作（commit graph、merge、rebase、cherry-pick、LFS）已发布三平台原生库，P/Invoke 层无需重写。
2. **Git/Commands 226 个命令是纯 C# 业务层** —— 调用 biturbo，跨平台基本零改动。
3. **架构已分平台接缝** —— `ServiceLocator` 把 7 类平台能力（IDispatcher / IClipboardService / IToastNotificationService / IWindowManagerService / IAppContext / IDesignModeService / ITimerService）抽象为接口，各有一个 `Wpf*` 实现。**Avalonia 端只需为每个接口补 `Avalonia*` 实现，业务层零改动。**
4. **AI 渲染逻辑跨平台** —— Markdown→HTML 实际走 biturbo，WebView2 仅做最终渲染，可改用 `Markdown.Avalonia` 彻底甩掉 WebView2 这个最大依赖。

> 真正「需要改」的 ≈ 245 个 XAML（全量语法转换）+ 约 120 个含平台依赖的 .cs 文件，占总量（1,402 cs + 245 xaml）约 25%。但 XAML 几乎 100% 要改语法，UI 层是「语义保留、语法重写」。

## 5. 风险清单（按可能性 × 影响）

| 风险 | 影响 | 缓解 |
|---|---|---|
| AvalonEdit 与 AvaloniaEdit API 差异 | 编辑器重写超预估 | 先建最小可用的 Diff 编辑器 PoC 验证 |
| WebView2 流式 AI 在 Linux/macOS 原生 webview 可用性 | AI 界面需返工 | 决策：用 Markdown.Avalonia 纯渲染，绕开 webview |

| 主题热重载语义丢失 | 体验回退 | 保留原热重载设计，映射到 Avalonia 主题切换 |

## 7. 给立项方的建议

1. **不要让业务工程师碰 Git 引擎**——biturbo 三平台已就绪，重写的 ROI 为负。
2. **先打 AvalonEdit 替代的 PoC**（最大不确定项），再全面铺开 UI 迁移。
3. **把本目录的 62 张截图 + `操作步骤.md` + `源码映射.md` 作为回归基线**，每个平台迁移完一个界面就对照一次。
4. **AI 界面优先评估 Markdown.Avalonia 路线**，能砍掉 WebView2 这一个高危依赖。
5. 团队配置建议：**1 名架构（接缝/服务层）+ 2–3 名 UI 迁移 + 1 名测试/CI**，4–5 人 3–5 个月。
